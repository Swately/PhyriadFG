## The four findings that steer the project

1. **DLSS 5 consumes ONLY colour + motion vectors + carried temporal state + scalar artistic values.**
   No G-buffer, no depth, no geometry — NVIDIA on the record. The albedo/normals in its marketing are
   TRAINING-time supervision, not inference inputs. That is exactly the signal set PhyriadFG already
   has, so the no-swapchain-hook constraint does NOT disqualify this class of technique.
2. **Architecture: a compact one-step pixel-space diffusion transformer**, ~148M parameters in FP8.
   Models A/B/C are three separate networks; intensity is two separate scalars.
3. **DLSS 5 has NO text-prompt conditioning.** The operator's idea is a genuine departure, not a
   re-implementation of what NVIDIA shipped.
4. **Diffusion at gameplay rates is excluded by measurement, not by pessimism.** Four RTX 4090s for
   24 fps at 512x512; one distilled step costs 10.65 ms at 512x512 on a 4090 with TensorRT, against a
   4.16 ms TOTAL budget at 240 Hz; nobody has published real-time diffusion at 1080p on one consumer GPU.

## Can any DLSS component be driven from OUTSIDE the rendering application (a capture-based overlay with colour pixels only)? — NGX/Streamline initialisation and input requirements, DLSS SR / FG / RR / DLSS 5 input contracts, and what external-capture projects (Lossless Scaling, OptiScaler, DLSS-NR-on-AMD) actually do.

- **Streamline (the framework NVIDIA ships DLSS through) must be initialised inside the rendering application's process, BEFORE that application makes any DXGI/D3D/Vulkan call, and must be handed the application's own rendering device.**
  - ProgrammingGuide.md: 'Requested feature DLLs are loaded during `slInit` call. This is (and must be) done before any DX/VK APIs are invoked'; 'To ensure correct functionality in any scenario the app must call `slSetD3DDevice` after the main device is created'; for Vulkan 'the following API MUST be used to inform SL about the Vulkan specific information... to provide Vulkan device, instance information to SL'. Also 'slInit must NOT be called within DLLMain entry point'. An external overlay process cannot satisfy 'before any DX/VK APIs are invoked' for a device it does not own, and cannot supply the game's ID3D12Device/VkDevice.
  - *PRIMARY (NVIDIA's own SDK documentation, NVIDIA-RTX GitHub) · confidence high* — https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuide.md
- **Streamline evaluates every feature on a command buffer created on the same device — i.e. the caller must be recording into the game's own command list, on the game's own queue.**
  - ProgrammingGuide.md, slEvaluateFeature: 'cmdBuffer Command buffer to use (must be created on device where feature is supported)'. Resource tagging is per-frame and per-viewport: 'Frame and viewport must match whatever is used to set common and or feature options and constants'.
  - *PRIMARY · confidence high* — https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuide.md
- **The lower-level NGX API (what Streamline's DLSS plugin wraps) has the same hard binding: init takes the application's ID3D12Device, and create/evaluate take an OPEN, RECORDING command list whose node mask includes that device.**
  - NGX Programming Guide: 'NVSDK_NGX_D3D12_Init(unsigned long long InApplicationId, const wchar_t *InApplicationDataPath, ID3D12Device *InDevice, NVSDK_NGX_Version InSDKVersion = NVSDK_NGX_Version_API)'. CreateFeature/EvaluateFeature: 'Command list to use to execute GPU commands. Must be: - Open and recording - With node mask including the device provided in NVSDK_NGX_D3D12_Init - Execute on non-copy command queue.' Also 'NGX will modify D3D12 command list state, therefore, the calling process should save or restore its own D3D state before and after calling'. Note the phrase 'the calling process' — NGX assumes it IS the rendering process.
  - *PRIMARY (NVIDIA docs) · confidence high* — https://docs.nvidia.com/ngx/latest/programming-guide/index.html
- **NGX/DLSS also requires an NVIDIA-issued Application ID — it is not an anonymous library call.**
  - NGX Programming Guide, InApplicationId described as 'Unique Id provided by NVIDIA'. (In practice recent SDKs also accept a project-ID form, but the identity parameter is mandatory.)
  - *PRIMARY · confidence medium* — https://docs.nvidia.com/ngx/latest/programming-guide/index.html
- **DLSS Super Resolution requires depth AND motion vectors as mandatory inputs, plus jittered colour and per-frame camera constants. None of these exist in a captured finished frame.**
  - ProgrammingGuideDLSS.md: 'DLSS requires depth, motion vectors, render-res input color and final-res output color buffers.' Tags: sl::kBufferTypeScalingInputColor, sl::kBufferTypeScalingOutputColor, sl::kBufferTypeDepth, sl::kBufferTypeMvec. Exposure is the ONLY optional one: 'If sl::kBufferTypeExposure is NOT provided or dlssOptions.useAutoExposure is set to be true then DLSS will be in auto-exposure mode'. Constants: 'Various per frame camera related constants are required by all Streamline features and must be provided if any SL feature is active'; camera matrices 'row-major and should not contain any jitter offsets'; consts.mvecScale required.
  - *PRIMARY · confidence high* — https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS.md
- **DLSS Frame Generation requires MORE engine-internal data than Super Resolution — depth, dense motion vectors, a HUD-less colour buffer, and a separate UI buffer — and additionally takes over the swapchain and mandates Reflex integration.**
  - ProgrammingGuideDLSS_G.md: motion vectors must be a 'Dense motion vector field (i.e. includes camera motion, and motion of dynamic objects)'; the Hudless buffer 'Should contain the full viewable scene, without any HUD/UI elements in it'; 'For the best image quality, it is critical to provide a Hudless (pre-UI) buffer and a UI buffer'; 'Backbuffer (automatically intercepted via the Streamline swap chain)'; 'It is required for sl.reflex to be integrated in the host application'; presentation goes through an async 'SL pacer'. A capture-based overlay by definition only ever sees the composited, HUD-included final frame — the hudless/UI separation is structurally unavailable.
  - *PRIMARY · confidence high* — https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideDLSS_G.md
- **Even Streamline's 'manual hooking' mode — the escape hatch for engines that cannot use the interposer — still requires the application itself to route its own swapchain, device and present calls through Streamline proxies. It is not an external-process mode.**
  - ProgrammingGuideManualHooking.md mandates hooks on IDXGIFactory::CreateSwapChain/CreateSwapChainForHwnd/CreateSwapChainForCoreWindow, IDXGISwapChain::Present/Present1/GetBuffer/ResizeBuffers/GetCurrentBackBufferIndex/SetFullscreenState, ID3D12Device::CreateCommandQueue, and on Vulkan vkCreateSwapchainKHR/vkDestroySwapchainKHR/vkGetSwapchainImagesKHR/vkAcquireNextImageKHR/vkQueuePresentKHR. 'One should use native interfaces EVERYWHERE in the host application EXCEPT for the APIs which are hooked by SL.' Also: 'you must ensure the common plugin's presentCommon() function is called every frame.' Every one of these is a call the GAME makes; an overlay that never touches the game's swapchain cannot make them.
  - *PRIMARY · confidence high* — https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideManualHooking.md

**Implications for PhyriadFG:** BLUNT ANSWER TO THE MAKE-OR-BREAK QUESTION: No. No DLSS component that matters can be driven from outside the rendering application, and this is not a gap in tooling — it is the API's shape.

The binding is triple, and each layer alone is fatal for a capture-based overlay:

1. PROCESS/DEVICE BINDING. slInit must run 'before any DX/VK APIs are invoked' and slSetD3DDevice must receive the app's own device; NGX's NVSDK_NGX_D3D12_Init takes an ID3D12Device* and its Create/Evaluate take an OPEN, RECORDING command list on that device. PhyriadFG owns a different process, a different device, and a different command queue. Even Streamline's 'manual hooking' escape hatch is a list of calls the GAME makes (CreateSwapChain, Present, CreateCommandQueue, vkQueuePresentKHR) — it is an in-process mode with a different plumbing style, not an out-of-process mode. Nothing in the SDK contemplates an external consumer.

2. DATA BINDING — the one PhyriadFG cannot buy its way out of. DLSS SR needs depth + motion vectors (mandatory; only exposure is optional). DLSS-G needs depth + dense MVs + a HUD-LESS colour buffer + a separate UI buffer, plus mandatory Reflex, plus ownership of the swapchain. DLSS-RR needs a full G-buffer (diffuse albedo, specular albedo, normals, roughness, specular hit distance). And DLSS 5 itself — the thing that prompted this — is conditioned per NVIDIA Research on 'the current rendered frame, engine motion vectors, carried temporal state, and artistic-direction values', with NVIDIA's GeForce article adding albedo, lighting and normals. DLSS 5 is a G-buffer-conditioned diffusion model, NOT a colour-space post-process. WGC/Desktop Duplication hand you one composited RGB plane. The gap is categorical.

3. LICENCE BINDING. Even if 1 and 2 were solved, §4.b forbids distributing the SDK 'as a stand-alone product' and §4.a forbids reverse engineering. A general overlay applying DLSS to arbitrary third-party games is exactly the prohibited shape.

Plus the hardware fact: DLSS 5 is RTX 50-only and the operator has a 4090. That alone ends any 'run DLSS 5' plan today, independent of everything above.

THE THREE-WAY VERDICT HE ASKED FOR, for colour-pixels-only capture:
(a) IMPOSSIBLE — DLSS Super Resolution, DLSS Frame Generation, DLSS Ray Reconstruction, DLSS 5 Neural Rendering, and DLAA. All require engine-internal data that does not survive compositing, and all require in-process device/command-list access. There is no degraded mode; you cannot feed a zeroed depth buffer and a self-estimated MV field to DLSS SR and get anything but garbage, because DLSS's temporal accumulation trusts those inputs as ground truth. Do not spend a week finding this out empirically.
(b) POSSIBLE BUT DEGRADED — nothing from the DLSS family. The 'degraded' slot is occupied by what PhyriadFG ALREADY does: self-estimated optical flow from consecutive captured frames. That is the correct and only design for this constraint, and it is the same one Lossless Scaling reached.
(c) GENUINELY USABLE — NIS (NVIDIA Image Scaling) and only NIS: colour-in/colour-out, non-temporal, non-AI, open source, runs on any GPU, needs no device sharing. It is a 6-tap directional scaler with adaptive sharpening. It is genuinely droppable into PhyriadFG's overlay today. It is also nowhere near what he wants — it sharpens, it does not relight.

WHAT THIS MEANS FOR HIS ACTUAL GOAL (a prompt-driven AI look filter inside PhyriadFG):
The research validates the plan by elimination. Lossless Scaling — the commercial product with the identical architectural constraint — wrote its OWN model from scratch ('a proprietary machine learning model developed from scratch specifically for Lossless Scaling') rather than calling anyone's. That is a market-tested answer to 'should I try to borrow a vendor model or build my own', and the answer is build your own. His instinct is correct and he should stop looking for a DLSS hook.

Three engineering consequences he should carry forward:
- His model must be COLOUR-CONDITIONED ONLY, by construction. Any architecture he reads about that takes albedo/normals/depth (which is all of DLSS 5, and most neural-rendering papers) is not portable to his input. He is in the image-to-image / video-to-video family, not the neural-rendering family. Different literature.
- TEMPORAL STABILITY is his hardest problem and he gets no help. DLSS 5 buys stability with engine MVs plus carried temporal state; he has only his own estimated flow — which PhyriadFG already computes and which the convergence spine (R0–R7) already hardened. That existing flow estimator is the asset to build the filter ON TOP OF, not a separate subsystem. His fg_core.comp flow field IS his substitute for engine MVs.
- The COST BUDGET is the real risk, not feasibility. NVIDIA publishes no isolated ms figure for the DLSS 5 pass. The only cost datapoint anywhere is the AMD port collapsing Cyberpunk from 80+ fps to 11-12 fps at 1080p (alpha, wrong hardware, non-comparable — but it is the only number in existence). A one-step pixel-space diffusion model at 4K is nowhere near a 240 Hz overlay budget on a 4090 that is also running the game. He should design for a small distilled network and measure ms/frame at his target resolution before committing to an architecture, and he should treat 'real-time text-prompted diffusion over game frames' as unestablished-in-the-wild rather than assumed-solved.

One caution about the prompt idea specifically: DLSS 5's 'artistic-direction values' are developer-authored numeric controls baked in at integration time, NOT free-text prompts. There is no shipping precedent I could find for a real-time text-prompted game filter. That makes his idea genuinely novel — and correspondingly unproven. Novel is not the same as validated; the fact that nobody ships it is weak evidence it is hard, not evidence the field missed something.

**Implications for PhyriadFG:** THE SHORT ANSWER: the licence is not the wall the operator probably expected, and the wall that actually stops him is somewhere else.

WHAT THE LICENCE ALLOWS, MORE THAN EXPECTED. Redistribution of the DLSS DLLs by a third party is permitted, and the conditions are structural rather than identity-based. Clause 1(c) lets you distribute SDK binaries "as incorporated in object code format into a software application"; clause 2(a) requires only that the application have "material additional functionality, beyond the included portions of the SDK" — PhyriadFG plainly does; clause 4(b) forbids only shipping the SDK "as a stand-alone product". Critically, NOTHING in the licence says the application being enhanced must be one the licensee wrote. The clauses say "a software application", never "your game". And Supplement §4 explicitly contemplates "a plug-in to a commercial application" as a licensed shape, with a pre-release notification duty attached. So the pure legal question the operator asked — may an external overlay drive DLSS on a program it did not write — has no clause forbidding it. It has no clause blessing it either; it is unaddressed territory, and the clauses that surround it (6.2's kill switch, 7.1(b)'s splash-screen attribution requirement) are written on the assumption the licensee controls the host application, which he would not.

WHAT THE LICENCE FORBIDS, EXACTLY AND WITHOUT AMBIGUITY. Clauses 4(a), 4(b) and 4(d) together shut down reverse engineering, decompilation, disassembly, modification of any non-sample portion, and circumvention of any technical limitation. The RTX 40 route that has been circulating — patching the leaked DLL's CUDA binaries so they run on Ada — trips all three at once. On an RTX 4090 that is not a grey area; it is the clearest breach in this entire space, and it is the only route by which the operator's actual hardware could run DLSS 5 today.

THE FACT THAT DECIDES IT ANYWAY. There is no publicly licensed DLSS 5. NVIDIA's own repos stop at DLSS 310.7.0 and Streamline 2.12.0, both dated 2026-06-23, with no August or September commits and no neural-rendering mention in any release note. The only DLSS 5 binary in existence outside partner studios is nvngx_dlssnr.dll (310.8.0.0, ~158 MB) that leaked out of an NBA 2K27 early-access build — a version number ahead of anything NVIDIA ever published. Clause 1(c) permits distributing "software and materials within the SDK"; a leaked file is within no SDK he was granted. Bundling it in PhyriadFG is outside every grant in the document, and PhyriadFG is a redistributed tool, not a private experiment — the exposure is real, not theoretical.

THE CONSTRAINT THAT MAKES THE LICENCE QUESTION MOOT. NVIDIA states DLSS 5 "takes a game's color and motion vectors for each frame as input". PhyriadFG has no engine motion vectors by deliberate design — it captures finished frames and estimates its own optical flow. Even a fully licensed DLSS 5 on supported hardware could not be fed correctly through the capture path, and the no-swapchain-hook constraint is the very thing that forecloses obtaining them. The architecture and the technology are incompatible before the lawyers arrive.

THE ONE GENUINELY GOOD PIECE OF NEWS, AND ITS EXPIRY DATE. The operator's stated goal is not to run DLSS 5 but to build his own prompt-driven equivalent, and the tempting shortcut is to imitate DLSS 5's look. On that: the RTX SDKs License contains NO restriction on using DLSS output to train, fine-tune or distil another model. I read all 19 sections and all 7 supplement sections; there is no output clause, no training clause, no derived-data clause. The only training language runs the other way — Supplement §2 grants NVIDIA rights over content he might send THEM. The anti-training and output-reverse-engineering clauses that do exist in NVIDIA's estate (SLA §8.4, §8.11, §8.10) live in the enterprise agreement governing AI Enterprise, vGPU and Networking, and do not reach the RTX SDKs. But two cautions, and they are not small. First, this permission is only as good as the licence he is actually under: the quoted text is the DLSS 4.x-era licence, and DLSS 5 being a generative model of a different character is exactly the occasion on which NVIDIA would attach new terms. Do not treat today's silence as a prediction. Second, the permission is narrow in kind — training on OBSERVED OUTPUT is unrestricted, but any step that involves opening the DLL to learn its architecture crosses into 4(a), and he cannot lawfully obtain DLSS 5 output on his hardware anyway without the patched-binary breach described above.

## What DLSS 5 actually IS, technically — inputs, pipeline position, architecture, models A/B/C, and integration path; assessed against PhyriadFG's capture-only, no-engine-data architecture

- **DLSS 5's model consumes ONLY the rendered colour frame plus motion vectors, carried temporal state, and artistic-direction values. It does NOT read G-buffer, geometry, depth, textures, or lighting buffers at inference. This is the single most important finding for the operator and it inverts the task brief's stated expectation.**
  - NVIDIA Research (ADLR), the primary technical page, states: "At inference, the model is conditioned on the current rendered frame, engine motion vectors, carried temporal state, and artistic-direction values." The words "At inference" and "conditioned on" are the load-bearing ones — this is the runtime input list, and it contains no G-buffer term.
  - *PRIMARY (NVIDIA Research / ADLR lab page) · confidence high* — https://research.nvidia.com/labs/adlr/DLSS5/
- **NVIDIA confirmed the colour+motion-vector-only input contract explicitly and on the record, and stated that material properties are INFERRED from the rendered frame rather than read from the engine.**
  - NVIDIA's Jacob Freeman, responding by email to YouTuber Daniel Owen: "Yes, DLSS 5 takes a 2D frame plus motion vectors as input" and "DLSS 5 only takes the rendered frame and motion vectors as inputs... Materials are inferred from the rendered frame." He also stated "The underlying geometry is unchanged" and noted it was "a very early preview of the tech." Reported 2026-03-20; original source is Daniel Owen's video (youtube.com/watch?v=D0EM1vKt36s). Corroborated across four independent outlets (Shacknews, TweakTown, VideoCardz, Notebookcheck) quoting the same exchange.
  - *SECONDARY reporting a direct, attributed NVIDIA statement (multi-outlet corroborated) · confidence high* — https://www.shacknews.com/article/148397/nvidia-dlss-5-generative-ai
- **DLSS 5 is limited to SCREEN SPACE. It has no understanding of ray tracing or off-screen information, and lacks access to PBR material properties, 3D geometry, and depth buffers — all of which it must guess.**
  - TweakTown, reporting the same Freeman exchange: DLSS 5 "takes only a scene's 2D-rendered frame and its motion vectors as input"; it "does not have access to 3D geometry, depth buffers, or PBR material properties" and "is forced to infer what the material is supposed to look like rather than reading these properties directly from the game engine." It relies on "semantic labeling to identify clusters of pixels as eyes, cheeks, lips, etcetera." Notebookcheck's account of the same exchange adds that NVIDIA confirmed DLSS 5 is "limited to screen space."
  - *SECONDARY reporting an attributed NVIDIA statement · confidence high* — https://www.tweaktown.com/news/110569/dlss-5-only-takes-2d-rendered-frames-and-motion-vectors-as-input-not-3d-game-engine-data-confirms-nvidia/index.html
- **The albedo / surface-normal / lighting data that NVIDIA's marketing page mentions is TRAINING-TIME supervision, not an inference-time input. This resolves the apparent contradiction between NVIDIA's consumer page and its research page.**
  - NVIDIA's GeForce page says the model "anchors directly to the rendered frame, by training to recognize engine data such as color, surface albedo, detailed lighting, and surface normals" — the verb is 'training'. The ADLR research page independently describes "consistency supervision from renderer-derived scene attributes" as a training mechanism used "to ground generation to authored scenes." Both phrasings place these buffers in training. At least one secondary outlet (XenoSpectrum) misread this as a runtime input list, claiming the system "receives internal renderer buffers: albedo, surface normals, and partial lighting information" — that claim is contradicted by NVIDIA's own inference-time description and by working third-party implementations that supply none of them.
  - *PRIMARY (NVIDIA GeForce announcement) cross-read against PRIMARY (ADLR) · confidence high* — https://www.nvidia.com/en-us/geforce/news/dlss-5-3d-guided-neural-rendering/
- **Independent working implementations prove the colour-only contract empirically: a ComfyUI wrapper runs the real DLSS 5 neural renderer on ordinary image and video files, with motion vectors estimated by classical optical flow and NO depth, geometry, texture, or lighting buffers at all.**
  - ComfyUI-DLSS5-Enhancer wraps "NGX feature 18" and feeds the native D3D12 worker an "RGBA8 frame" plus "FP16 motion vectors" that are estimated "from footage using dense optical flow (OpenCV DIS)" at render resolution, returning an "RGBA8 reconstructed frame".   - *PRIMARY (NVIDIA fps figures) + SECONDARY (multiplier analysis) · confidence medium* — https://www.nvidia.com/en-us/geforce/news/dlss-5-3d-guided-neural-rendering/
- **Documented failure modes when motion vectors are ESTIMATED rather than engine-supplied — directly predictive of what PhyriadFG would hit.**
  - DLSS5-Feeder README, on running the neural pass with optical-flow motion vectors: "Ghosting in fast motion due to estimation error"; "Softness on thin moving geometry"; "Warping artifacts around flames, flickering lights, and transparents (lighting changes misinterpreted as motion)"; "HUD processed alongside scene (no semantic separation)". The dlss5-bridge README summarises the substitute path as "lower quality", where "text softens and dense foliage smears". Optical-flow tuning exposed: grid 1/2/4 or shader-based (0), effort 5 (slow) / 10 (medium) / 20 (fast).
  - *COMMUNITY implementation (empirical failure-mode catalogue) · confidence high* — https://github.com/jlrouzies-fr/DLSS5-Feeder
- **DLSS 5 has NO text-prompt conditioning. Its only artistic steering is scalar intensities plus per-object masks. The operator's text-driven concept is therefore a genuine departure, not a re-implementation.**
  - ADLR's complete inference input list is "the current rendered frame, engine motion vectors, carried temporal state, and artistic-direction values" — no text encoder, no embedding input. The artistic-direction values are the Structure Intensity / Tone Intensity sliders and per-object masks described in SIGGRAPH coverage. NVIDIA additionally offers colour-grading overrides and per-element masking. No source in this survey describes any language conditioning anywhere in DLSS 5.
  - *PRIMARY (ADLR), reasoning from a complete stated input list · confidence high* — https://research.nvidia.com/labs/adlr/DLSS5/
- **Temporal stability is achieved by carrying explicit temporal state plus a history-reset signal on scene cuts — not by the model being frame-independent.**
  - NVIDIA: "By leveraging motion vectors directly from the game engine, DLSS 5 ensures every generated frame is stable, eliminating visual shimmering, swimming, or temporal drift even as players move." ADLR lists "carried temporal state" as an inference input and describes inference as "causal and deterministic" with "frame-to-frame temporal stability". The ComfyUI wrapper exposes a "history reset flag" for scene cuts with automatic luminance-threshold detection.
  - *PRIMARY (NVIDIA) + COMMUNITY (reset-flag mechanism) · confidence high* — https://www.nvidia.com/en-us/geforce/news/dlss-5-3d-guided-neural-rendering/

**Implications for PhyriadFG:** HEADLINE, AND IT REVERSES THE BRIEF'S PREMISE. The task brief assumed "a neural relighting model almost certainly needs more than colour". It does not. NVIDIA's own research page states DLSS 5 is conditioned at inference on the rendered frame, engine motion vectors, carried temporal state, and artistic-direction values — nothing else — and NVIDIA's Jacob Freeman said flatly that materials are INFERRED from the rendered frame, with no access to geometry, depth buffers, or PBR properties. The albedo/normals/lighting language on NVIDIA's consumer page is training-time supervision, not a runtime input; both NVIDIA texts use the word "training" for it. DLSS 5 is, in input terms, a screen-space filter over finished colour plus motion — which is EXACTLY the signal set PhyriadFG already captures. The operator's hard anti-cheat constraint (no swapchain hook, no engine data) is therefore NOT a disqualifier for this class of technique. That is the finding that should steer the project.

WHAT THIS BUYS HIM CONCRETELY. Three independent third-party implementations run the real DLSS 5 neural renderer with no engine cooperation at all: two ReShade bridges that synthesise a contract from estimated motion, and a ComfyUI wrapper that feeds it RGBA8 frames with motion vectors from OpenCV DIS optical flow and explicitly no depth, geometry, texture, or lighting buffers. PhyriadFG already estimates its own optical flow and already carries temporal state (FlowSet/FlowRing). The architectural template is confirmed working from exactly his position in the stack.

WHAT WILL HURT, ALREADY CATALOGUED. The Feeder README lists the failure modes of running this class of model on estimated motion: ghosting in fast motion, softness on thin moving geometry, warping around flames/flickering lights/transparents where lighting change is misread as motion, and — most relevant to a whole-window capture — the HUD being processed alongside the scene with no semantic separation. DLSS 5 solves that last one with developer-supplied per-element masks, which PhyriadFG cannot obtain from outside the process. He would need to derive UI masks himself (temporal stability of static screen regions is the obvious heuristic, and his existing flow field already gives him the raw material). Add the history-reset-on-scene-cut mechanism; the ComfyUI wrapper does it with a luminance-change threshold, which is cheap and worth copying.

THE REAL CONSTRAINT IS THE FRAME BUDGET, NOT THE INPUTS. At 240 Hz he has 4.16 ms total for everything. DLSS 5 is ~148M parameters in FP8 (third-party binary analysis, not NVIDIA-confirmed) and unofficial RTX 4090 testing showed roughly 135-145 fps falling to ~83 fps, implying about 4.5-5.3 ms for the neural pass alone — more than his entire budget, on his exact GPU, before any of PhyriadFG's own work. Treat that number as soft: leaked build, patched kernels, unstated resolution. But the order of magnitude is the message. A DLSS-5-sized model is not viable at 240 Hz on a 4090. Viable directions: run the filter at a fraction of output resolution and upsample (the Feeder notes work scales roughly linearly, 50% resolution ≈ 25% of the cost); run it on a subset of frames and reproject with his existing flow; or size the model an order of magnitude smaller. Note also that FP8 tensor throughput exists on Ada — the RTX 50 exclusivity is a kernel-compilation boundary, not a capability one, as the RTX 40 patched builds demonstrate — so he can target FP8 on the 4090 for his own model.

HIS TEXT-PROMPT IDEA IS GENUINELY NOVEL HERE. DLSS 5 has no language conditioning anywhere. Its entire artistic surface is two scalars (Structure Intensity for high-frequency detail, Tone Intensity for low-frequency lighting/colour), per-object masks, and colour-grading overrides — plus the coarse choice between three separately-trained networks A/B/C. So he is not re-implementing DLSS 5 with a prompt bolted on; he is proposing a different control modality. Design note in his favour: a text encoder runs once per prompt CHANGE, not per frame, so the prompt path is essentially free at runtime — the per-frame cost is only the cross-attention or FiLM-style modulation the embedding drives. That makes text conditioning cheaper than it sounds, and it is the one axis where he can beat NVIDIA rather than chase them.

ARCHITECTURE TO STUDY, NOT COPY. One-step pixel-space diffusion transformer, distilled from a larger foundation model. The one-step property is the whole trick — it is what makes a diffusion model real-time — and distillation-from-a-larger-teacher is the standard route to it. That is the literature he should be reading, not the DLSS SDK. Integration-wise there is nothing to reuse: no DLSS 5 programming guide exists in the public Streamline repo, the feature is an NGX call (feature 18) behind a closed, leaked DLL, and every third-party tool surveyed depends on that leaked binary — not a lawful basis for his own product.

The current ADLR page states the same input list, so the two converge and I rate the finding high-confidence — but no post-launch NVIDIA restatement exists, and most performance material circulating right now is pre-release, leaked-build, or marketing with Multi Frame Generation folded in.

**Implications for PhyriadFG:** THE ARCHITECTURAL VERDICT FIRST, because it eliminates most of the field before any performance question is asked.

PhyriadFG's no-hook constraint disqualifies every temporal upscaler on the market. FSR 2/3.1 require depth + motion vectors + camera jitter (primary: GPUOpen FSR SDK manual). XeSS requires jitter + MVs + depth (primary: Intel developer guide). Arm NSS requires accurate motion vectors and frame history (primary: model card). These are not soft requirements you can approximate from optical flow — their temporal reprojection assumes engine-exact vectors, and feeding estimated flow into them produces the smearing they were designed to avoid. Only two families survive the input contract: (a) purely spatial filters — FSR 1 (MIT) and NIS (MIT), both of which are hand-written filters, NOT neural; and (b) colour-only neural enhancers of the REGEN/Real-ESRGAN class, which survive the input test and fail the latency test.

Independently, FSR 4 is dead on this machine regardless of licensing: AMD gates it to RX 7000/9000 with SM 6.6 and falls back to FSR 3.1.5 elsewhere. The 2025 accidental MIT publication of FSR 4 source is a legal hazard with zero payoff on a 4090. Do not chase it.

THE BUDGET ARITHMETIC, which is where the real answer lives.

PhyriadFG presents at up to 240 Hz — a 4.17 ms TOTAL frame budget that already contains capture, optical flow, warp, MV consensus, composition and present. NVIDIA's own figure for a vendor-grade, tensor-core-native neural pass is ~3.25 ms for one 4K frame on a 4090 (DLSS 3 FG). Scaled to 1080p that is roughly 0.8 ms — and that is the FLOOR, achieved with full engine access and no capture path, in an uncontended measurement. The closest published colour-only academic analogue, REGEN, manages 'above 20 FPS' at 960x544 on a 4090, i.e. ~50 ms/frame — 12x over the entire 240 Hz budget, at a third of 1080p's pixels, with no game on the GPU. The gap between those two numbers (0.8 ms vs 50 ms) is the gap between 'a tiny MLP evaluated per-pixel' and 'a generative network'. Which side of that gap a design lands on is the whole engineering decision.

THE PROMPT-DRIVEN GOAL SPECIFICALLY: the honest finding is that it exists and is ~two orders of magnitude too slow. The June-2026 streaming edit-diffusion work hits 54.9 fps throughput on a 4090 — but at 512x512, and with p50 END-TO-END LATENCY of 272-513 ms. Throughput is not latency here; a 272 ms p50 means the overlay displays a quarter-second-old game. For a frame-generation overlay whose entire value proposition is latency, that is not a tuning problem, it is a category error. Its base weights are also gated behind a safety-review request process, so it is not even redistributable today. Recommend the operator treat 'text-prompt-driven look, applied to live gameplay at 240 Hz' as NOT ACHIEVABLE with 2026 technology on a 4090, and decide explicitly whether he wants (i) a real-time filter with a fixed or small parameterised look, or (ii) a prompt-driven filter that runs at 20-30 fps on a paused/slow scene or a secondary capture — because those are two different products.

THE VIABLE INCREMENTAL PATH, in order of cost:

1. NIS (MIT, HLSL+GLSL compute shaders, colour-only, no engine data) is a genuine drop-in for the existing Vulkan pipeline. FSR 1 (MIT, EASU+RCAS, explicitly no MVs or history) is the same class, with published costs of ≤0.40 ms at 4K Ultra Quality on 2021 enthusiast hardware — comfortably sub-budget at 1080p on a 4090. Neither is AI; both would improve the overlay's output today at near-zero risk. This is the only recommendation here that survives every constraint.

2. The MIT FidelityFX SDK 1.1.x branch ships AMD's OPTICAL FLOW and FRAME INTERPOLATION source. Given PhyriadFG's R5 FLOW work and the MV consensus pass already identified as the source of the 1.7 px low-phase error, that source is worth reading as a cross-check on the operator's own flow implementation even if not a line of it is adopted.

3. If a genuinely neural pass is wanted, the right primitive on this hardware is VK_NV_cooperative_vector — available on RTX 20XX+, so the 4090 qualifies, requiring driver ≥572.16 and Vulkan SDK 1.3.296.0, with RTXNS as the reference. It evaluates SMALL MLPs inside a compute shader, in the same Vulkan device and command stream PhyriadFG already owns, with no second runtime, no CUDA redistributables and no ONNX graph. That is the only neural option that is architecturally native to this application rather than bolted onto it. Its ceiling is a small per-pixel network — which is exactly the size class that fits the 4.17 ms budget, and exactly not the size class that does photoreal restyling. Note the extension is NVIDIA-vendor, not KHR: a PhyriadFG feature built on it works only on RTX and needs a clean fallback.

4. If an ONNX-graph model must be run, the runtime ranking for THIS application is: ncnn (BSD-3, Vulkan, explicitly no third-party runtime dependencies — shares the app's Vulkan device, zero deployment burden, unknown tensor-core efficiency) > TensorRT for RTX (fastest, <200 MB, Turing→Blackwell, engines portable across GPUs via on-device JIT, but a 15-30 s first-run build needing a cache, plus an NVIDIA licence acceptance) > ONNX Runtime + DirectML (only D3D12 needed, but Microsoft has it in 'sustained engineering' with new work moved to Windows ML) > ONNX Runtime + CUDA EP (worst: strict CUDA/cuDNN major-version pinning and hundreds of MB of NVIDIA DLLs on the end user's machine).

5. Licence hygiene: Magpie and OptiScaler are the obvious references and are both GPL-3.0. Read them, do not copy them. OptiScaler is additionally the anti-pattern — it DLL-proxies dxgi/d3d12 and hooks with Detours, the exact technique PhyriadFG refuses. That refusal remains PhyriadFG's differentiator and its main constraint simultaneously.

**Implications for PhyriadFG:** SHORT ANSWER TO THE OPERATOR'S BELIEF: half right, and the wrong half is the important one. Community git repos for DLSS DLLs are real, legitimate and well-run (DLSS Swapper, GPL-3.0, and its manifest builder) — but they do not carry DLSS 5, and NVIDIA itself publishes the DLLs on GitHub, so the community layer was never the primary source in the first place. Everything circulating as "DLSS 5 files" right now traces to one leaked pre-release binary pulled out of NBA 2K27's early-access build.

1. "HAVING THE FILES" IS MEANINGFUL IN PRINCIPLE — the weights really are self-contained. This is settled from two independent directions: the reverse-engineered nvngx_dlssnr.dll carries its weights as a PE resource (WEIGHTS_HT/1033, 147,695,410 bytes), and on the operator's OWN machine I confirmed that NVIDIA's driver-side "model store" at C:\ProgramData\NVIDIA\NGX\models\ is not a weights cache at all — its .bin files are whole PE images with MZ headers and NVIDIA DLSS version resources, and nvngx_package_config.txt names them outright as nvngx_dlss.dll / nvngx_dlssd.dll / nvngx_dlssg.dll. There is no separate weight download to chase. A DLL is the complete model.

2. BUT IT IS USELESS TO HIM IN PRACTICE, for three independent reasons, any one of which is fatal: (a) no public API — there is no nvsdk_ngx_defs_dlssnr.h anywhere, so the feature enum, parameter names and resource bindings needed to invoke DLSS-NR are simply not published; (b) no executable code path — the leaked build's 15 CUDA fatbins target sm_120 (Blackwell) only, so a 4090 cannot run it as compiled, and this is independent of whether Ada supports FP8 (it does); (c) licence — NVIDIA's RTX SDK licence says in terms "you may not distribute or sublicense the SDK as a stand-alone product", so PhyriadFG shipping any nvngx_*.dll is a licence violation, not a grey area. Worth noting for its own sake that RTX 50 exclusivity is NOT permanent — NVIDIA has said it plans to extend support to RTX 40 — but that is NVIDIA's roadmap, not a path he can build on.

3. THE GENUINELY ENCOURAGING FINDING, AND THE REASON THIS RESEARCH WAS WORTH DOING: DLSS 5 is a PIXEL-SPACE model. NVIDIA's own description is that it takes the finished rendered frame plus motion vectors, with developer masks as optional side-channel control; HotHardware calls it "a pixel-space per-frame diffuser". It is emphatically not a G-buffer consumer in the way Ray Reconstruction is. That is very close to PhyriadFG's envelope — captured colour frames plus self-estimated optical flow — and it means his hard anti-cheat constraint (no swapchain hook, no engine internals) does NOT disqualify the class of technique he wants to build. NVIDIA has effectively validated that a colour+motion neural relighting filter is coherent. CAVEAT, and he should not skip it: sources conflict on depth. The reverse-engineering write-up lists depth among the inputs; HWCooling says explicitly there is none. If depth turns out to be load-bearing rather than optional, that is the one input PhyriadFG structurally cannot obtain, and it would change the difficulty of his own model substantially. This is the single most important open question for him and it is not currently answerable from public material.

4. THE COST PROFILE IS THE REAL WALL, AND IT IS WORSE THAN THE MARKETING SUGGESTS. Independent measurement on an RTX 5070 Ti at 1440p DLSS Quality: 68.9 FPS with neural rendering on versus ~240 FPS with it off — roughly a 3.5x reduction, matching NVIDIA's own admission of a 50-60% performance cost. NVIDIA's 370 FPS 4K headline is only reachable with upscaling plus up to 6x frame generation stacked on top. For a project whose stated presentation target is 240 Hz through a borderless overlay, this is the number that should reset expectations: a ~148M-parameter FP8 transformer running per-frame at 1440p is roughly two orders of magnitude away from a 240 Hz budget on a 4090, and he would additionally be paying it on a GPU that is simultaneously running the actual game. His model will need to be dramatically smaller than DLSS-NR, or run at reduced rate/resolution with temporal reuse — which, given he already has FlowSet/FlowRing and a working temporal spine from R5, is the natural place to spend the engineering.

5. FOR THE TEXT-PROMPT GOAL SPECIFICALLY, DLSS 5 IS NOT A TEMPLATE — AND THAT IS FINE. Its control surface is three fixed weight sets (A/B/C) plus two independent scalars, Structure Intensity (high-frequency: ambient occlusion, reflections, subsurface scattering) and Tone Intensity (low-frequency: broader lighting and colour response), plus per-object masks. Nothing about it is prompt-conditioned; the gist calls it "latent-conditioned", which is a fixed latent, not a text encoder. So he is not reimplementing DLSS 5 with a prompt bolted on — he is building a different thing. What IS worth stealing verbatim is the control decomposition: separating structure from tone as independent axes is a genuinely good design he can map a prompt onto, and NVIDIA confirmed switching between A/B/C costs no performance, which tells him weight-set switching at runtime is cheap enough to expose as a user-facing control.

6. PRACTICAL NOTE ON HIS MACHINE: he is on driver 32.0.16.1088 (2026-07-21), older than the 616.64 WHQL that enables DLSS 5, and his local NGX config has no [dlssnr] section — consistent and expected. If he wants to study how NVIDIA actually packages a shipping NGX feature, those local files plus the official NVIDIA/DLSS repo headers are the legitimate material to read, and he already has both on disk.

## Prompt-driven real-time image-to-image filtering: 2026 state of the art, and what is actually reachable inside PhyriadFG (capture-only, no engine data, single RTX 4090, 1080p, up to 240 Hz present)

- **The single most relevant 2026 measurement: a prompt-conditioned streaming diffusion stylizer peaks at 54.9 fps on an RTX 4090 — but only at 512x512, with batch 8–16, and end-to-end latency of 0.5–1.0 seconds.**
  - Paper: 'Inverting the Streaming-Diffusion Bottleneck: Video-Rate MLLM-Conditioned Edit Diffusion on a Consumer GPU' (Yoshiyuki Ootani, arXiv 2606.05981, submitted 2026-06-04, revised 2026-07-15). Measured: 27.4–29.6 fps sustained on RTX 3090 Ti at 512x512, batch 8–16; 'Peak performance: 54.9 fps (RTX 4090), 74.1 fps (RTX 5090)'. Pipeline: 0.39B distilled U-Net, K=1 denoising step, Qwen3-VL 2.13B text encoder, ControlNet-LLLite temporal adapter (~13M params), PyTorch 2.6 + torch.compile (TensorRT dropped due to FP16 overflow with MLLM outputs). Latency table (B=16): Qwen3-VL text encoder 466.9 ms/batch = 29.2 ms/frame; VAE encode 161.5 ms = 10.1 ms/frame; U-Net 302.7 ms = 18.9 ms/frame; VAE decode 190.3 ms = 11.9 ms/frame. Table III: B=8 -> 27.4 fps, p50 272 ms, e2e p50 0.506 s; B=16 -> 29.6 fps, p50 513 ms, e2e p50 1.013 s. NO evaluation above 512x512 anywhere in the paper.
  - *primary (arXiv preprint, single author, not peer-reviewed) · confidence medium-high on the numbers as reported; medium on generalization — the authors admit in-domain numbers use an adapter trained on the same 10 DAVIS sequences it is evaluated on, and held-out prompts degrade ~2x* — https://arxiv.org/html/2606.05981v1
- **That same paper independently confirms PhyriadFG's optical flow field is the exact input this class of method needs — and that computing it is a real bottleneck they had to fight.**
  - The method warps the previous decoded frame with optical flow and feeds it as ControlNet-LLLite conditioning. 'The paper employs Farnebäck flow for warping the previous decoded frame as the ControlNet-LLLite conditioning input. They validate against RAFT-Large, finding agreement within ±0.7%.' Cost: 'the unoptimized path shows CPU Farnebäck consuming ~848ms of an 882ms spike (96% attribution)'; they mitigate with 8 worker threads and async prefetch, cutting p95 latency 1439 ms -> 756 ms.
  - *primary (arXiv preprint) · confidence high — the flow-as-conditioning role is explicit; PhyriadFG already produces a GPU dense flow field per frame pair, which removes the 96%-of-spike CPU cost this paper had to engineer around* — https://arxiv.org/html/2606.05981v1
- **Full video-diffusion models (the Wan/CausVid/Self-Forcing family) are out of reach on one 4090. The best open system needs FOUR RTX 4090s to hit 24 fps at 512x512.**
  - StreamDiffusionV2 (arXiv 2511.07399, Best Research Paper, MLSys 2026). Measured table: '1.3B Model on RTX 4090 (4 GPUs, PCIe): 512x512: 24 FPS; 480p: 16 FPS (No batching results due to memory constraints)'. On 4x H100 with NVLink the same 1.3B model reaches 61.57 fps at 512x512 (1 step) and 42.26 fps at 480p; the 14B model reaches 58.28 fps at 512x512 (1 step), dropping to ~31.62 fps at 4 steps. Time-to-first-frame '0.47s and 0.37s at 16 FPS and 30 FPS video throughput'. Base models are Wan2.1-T2V 1.3B / 14B; Apache-2.0.
  - *primary (arXiv paper + official GitHub) · confidence high* — https://arxiv.org/html/2511.07399v1
- **Krea Realtime 14B — the flagship open-weights real-time video model — gets 11 fps on a single B200 and requires 40 GB VRAM. A 24 GB 4090 cannot load it.**
  - Krea (2025-10-20): 14B params, based on Wan 2.1 14B, self-forcing distillation. 'On a single NVIDIA B200 GPU, it achieves a text-to-video generation rate of 11 FPS with only 4 inference steps'; first frames in ~1 s. Weights + inference code under CC BY-NC-SA 4.0 (non-commercial, share-alike); 'recommends an NVIDIA GPU with at least 40GB of VRAM, and notes roughly 30GB of checkpoint storage'. Vendor-reported conditions, resolution not stated.
  - *primary (vendor blog + HF model card) · confidence high on VRAM/licence; medium on the 11 fps figure (vendor test conditions, resolution unstated)* — https://www.krea.ai/blog/krea-realtime-14b
- **Daydream Scope (the practical open-source runner for these pipelines) reports ~16.6 fps on TWO RTX 4090s for StreamDiffusionV2 at 1 step, without TensorRT or quantization.**
  - Scope is an Apache-2.0 open-source runner supporting StreamDiffusion V2, LongLive, Krea Realtime, RewardForcing and MemFlow, with VACE integration for depth/scribble/optical-flow control videos. Reported: '~16.6 FPS on 2x 4090 (1-step) without TensorRT/quantization for StreamDiffusion V2'; 'Most pipelines are optimized for 24GB GPUs like the RTX 4090 or RTX 5090, while Krea Realtime's 14B model requires 32GB+ VRAM.' Community alpha as of the Nov 2025 launch.
  - *secondary (aggregated from Daydream docs/HF card and launch coverage); the HF README itself did not carry the benchmark table when fetched · confidence medium — I could not read the fps table directly off a primary page; resolution for the 16.6 fps figure is not established* — https://huggingface.co/daydreamlive/scope
- **The realistic 'everything optimized, one 4090' number for a per-frame distilled diffusion pipeline WITH structural control is ~14–15 fps at 512x512.**
  - ComfyStream workflow by yondonfu: 'an output FPS of ~14-15 for a video stream with an input FPS of 14fps'. Conditions: RTX 4090, Ubuntu, driver 550.127.05, CUDA 12.5, PyTorch 2.5.1; resolution 512x512; Dreamshaper 8 (SD1.5) with a 1-step DMD-distilled UNet compiled to an fp8 TensorRT engine; TAESD VAE via torch.compile; v11f1p_sd15_depth ControlNet fp16; DepthAnythingV2 as an fp16 TensorRT engine.
  - *primary (practitioner's own measured config, published as a reproducible workflow) · confidence high on the number and its conditions* — https://gist.github.com/yondonfu/592a04e075e790981cd401124e0d84e4
- **Structural control (the thing that stops a diffusion filter inventing new geometry) costs a further 20–30% of frame time — measured on a 5090 at 368x640, i.e. far below 1080p.**
  - 'Adapting VACE for Real-Time Autoregressive Video Diffusion' (Ryan Fosdick / Daydream, arXiv 2602.14381, 2026-02-16). Table 5, LongLive 1.3B on RTX 5090 32GB, 368x640, 12 frames/chunk, 4 denoising steps, bf16, SageAttention: baseline 539 ms / 22.3 fps / 13.2 GB; +Depth Control 698 ms / 17.2 fps / 14.6 GB; +Inpainting 698 ms / 17.2 fps / 14.6 GB.   - *primary (arXiv, Daydream) · confidence high* — https://arxiv.org/html/2602.14381v1
- **StreamDiffusion's famous '91.07 fps on one RTX 4090' is a per-frame image-diffusion throughput figure whose resolution the paper never states in the text — treat it as 512x512 and as throughput, not latency.**
  - 'image generation to reach speeds of up to 91.07 fps on a single RTX 4090 GPU'. Table 1 gives per-inference times on RTX 4090 with TensorRT: 1 step 10.65 ms, 4 steps 26.93 ms, 10 steps 62.00 ms. Hardware: RTX 4090 + i9-13900K, Ubuntu 22.04.3. Pipeline: LCM / LCM-LoRA / SD-Turbo, TensorRT, TAESD lightweight VAE, Stream Batch. When asked directly for the throughput resolution, the paper text does not state it; the fps headline's exact configuration is 'not detailed in main text'.
  - *primary (arXiv) · confidence high on the ms-per-step numbers; LOW on any 1080p reading of the 91 fps figure — the resolution is genuinely unstated and this number is routinely quoted without its conditions* — https://arxiv.org/html/2312.12491v2
- **Even NVIDIA's own hand-tuned real-time diffuser costs roughly 70% of the framerate at 1440p on Blackwell, and it needs developer-authored engine-side masks. This is the honest ceiling reference for what a per-frame diffuser costs at game resolutions in 2026.**
  - HotHardware's DLSS 5 testing, GeForce RTX 5070 Ti desktop, 2560x1440, Quality DLSS: with DLSS 5 NR 68.9 fps avg / 52.3 fps 1% low; without DLSS 5 NR ~240 fps avg / 168.2 fps 1% low; Dynamic MFG on top 152.3 fps. Three model variants exist, unnamed. An RTX 5090 Mobile at 175 W 'could not maintain playable framerates'.
  - *secondary (hands-on press testing, three days after launch) · confidence medium-high on the measured fps; medium on the architecture wording (press paraphrase, not NVIDIA's own doc). DLSS 5 is RTX 50-only with no RTX 40 fallback path — it is not an option on the operator's 4090 regardless.* — https://hothardware.com/news/nvidia-dlss-5-neural-rendering-tested
- **Text-conditioned FEED-FORWARD style transfer is the family that actually fits the operator's architecture: the prompt is encoded once, and only a small conv net runs per frame.**
  - FastCLIPstyler / EdgeCLIPstyler (arXiv 2210.03461). Measured per-image runtimes: FastCLIPstyler 70.4 ms on an RTX 2070 SUPER (1,770.7 ms on a 6-core i5); EdgeCLIPstyler 24.9 ms on the RTX 2070 SUPER (390.3 ms on i5); '730x faster' than the original optimization-based CLIPstyler. Architecture: a text-style prediction network maps a 512-d CLIP text embedding through four hidden layers (256/256/150/150, leaky-ReLU 0.2, tanh output) to a 100-d style representation, which then drives a pre-trained Ghiasi-style application network. EdgeCLIPstyler swaps CLIP for a 768-d Sentence-BERT embedding and five hidden layers. Test rig: 6-core i5, 16 GB RAM, single 8 GB RTX 2070.
  - *primary (arXiv) · confidence high on the runtimes; the paper does NOT state the output resolution, which materially limits how far these numbers can be projected* — https://arxiv.org/pdf/2210.03461
- **The prompt->parameters step is a one-shot cost, not a per-frame cost, and it lands in the 1.4–1.6 second range with a small distilled model. That is entirely acceptable for a filter you retune by typing.**
  - 'Visual Editing with LLM-based Tool Chaining' (arXiv 2410.02952). Measured: '1.63s for Llama-2-7b-chat-hf on an A100 GPU'; '1.38s for FlanT5-base on an L4 GPU' — covering all three tools in a single inference pass. Models: Llama-2-7b-chat-hf with LoRA (33.5M trainable) and FlanT5-base (250M), distilled from GPT-3.5-Turbo. Emitted parameters: Global Adjust with 14 params (exposure, contrast, brightness, highlights, shadows, saturation, vibrance, temperature, tint, linearOffset, hue, bloom, sharpen, structure); Selective Adjust with 12 (six colour ranges x saturation/luminance); Filters (LUT choice from 24 presets + 0–100 intensity).
  - *primary (arXiv) · confidence high* — https://arxiv.org/html/2410.02952v2
- **The 'LLM emits a shader from a prompt, compiled at runtime' idea is already published and working on a live passthrough video feed — it is the cheapest version of the operator's exact concept.**
  - ShadAR (arXiv 2602.17481, submitted 2026-02-19; ISMAR 2025 Adjunct, and CHI 2026 Extended Abstracts, DOI 10.1145/3772363.3799378). Pipeline: voice captured and transcribed with Whisper, sent to a prompt-engineered LLM (OpenAI o3-mini), which emits HLSL; 'The generated shader is compiled in real-time and applied to the AR headset's passthrough viewport.' Demonstrated uses: colourblindness simulation, underwater look, colour highlighting.
  - *primary (arXiv/IEEE/ACM published) · confidence high that the system exists and works on live passthrough; LOW on any performance figure — generation latency, framerate and hardware are not disclosed on the pages I could reach (the full-text review site returned HTTP 429)* — https://arxiv.org/abs/2602.17481
- **The LUT path is essentially free at 1080p and scales to 4K without retraining — a learned model under 600K parameters processes a 4K frame in under 2 ms on a six-year-old GPU.**
  - Zeng et al., 'Learning Image-adaptive 3D Lookup Tables for High Performance Photo Enhancement in Real-time'. 'The model contains less than 600K parameters and takes less than 2 ms to process an image of 4K resolution using one Titan RTX GPU.' Architecture: several basis 3D LUTs plus a small CNN that runs on a DOWNSAMPLED copy of the frame to predict fusion weights. Critically: 'A model trained on the 480p resolution can be directly applied to images of 4K (or higher) resolution without performance drop.'
  - *primary (arXiv + official GitHub) · confidence high* — https://arxiv.org/abs/2009.14468
- **Generating a LUT with an expensive model ONCE and then applying it per-frame in a shader is a published, validated architecture pattern — and it is the pattern that makes a prompt-driven filter compatible with a 240 Hz cadence.**
  - 'Video Color Grading via Look-Up Table Generation' (Shin et al., ICCV 2025, pp. 19141–19152; arXiv 2508.00548). 'the key idea of explicitly generating a look-up table (LUT) for color attribute alignment between reference scenes and input video via a diffusion model' — a two-stage diffusion process produces a 3D colour LUT from a reference image plus source frames, 'allow[ing] for color grading without loss of structural details in video frames while achieving fast inference'. Code and pretrained models released.
  - *primary (ICCV 2025 paper + official GitHub) · confidence high on the architecture; the paper is REFERENCE-IMAGE conditioned, not text conditioned — swapping in a CLIP text embedding is an unvalidated extension, and I could not extract its LUT-generation inference time or fps from the abstract page* — https://arxiv.org/abs/2508.00548
- **A 3D LUT applied per frame is a pure per-pixel function, which means it cannot flicker. Temporal stability comes free — the only source of shimmer is you changing the LUT, which you control.**
  - This follows from the LUT formulation used in both Zeng et al. and the ICCV 2025 paper: the per-frame operation is a trilinear lookup in a fixed 3D colour cube, deterministic and content-independent frame to frame. Zeng et al. run the weight-predicting CNN on a downsampled frame; if that runs per-frame it can introduce slow drift, but slewing the fused LUT over time removes it. Contrast with per-frame diffusion, where the entire literature exists to fight flicker.
  - *inference from primary sources (my reasoning, not a quoted claim) · confidence high on the mechanism; flagged explicitly as my synthesis rather than a cited measurement* — https://arxiv.org/abs/2009.14468
- **Temporal stability in feed-forward style transfer is bought at TRAINING time with an optical-flow loss, so it costs nothing at runtime. This is a real architectural advantage over diffusion.**
  - ReCoNet: 'a real-time coherent video style transfer network that achieves an inference speed over 200 FPS on a single modern GPU' (arXiv 1807.01197, 2018). The temporal loss is a training-time construct; no flow is needed at inference. I could not extract the paper's exact evaluation resolution or GPU model — the PDF did not parse — so the 200 fps figure is unconditioned and should not be relied on quantitatively.

**Implications for PhyriadFG:** THE HONEST ANSWER: the operator's idea is buildable, but not as a diffusion model. Diffusion is excluded by measurement, not by pessimism — and the exclusion is not close.

WHY DIFFUSION IS OUT ON THIS HARDWARE. The best open streaming video-diffusion system needs FOUR RTX 4090s to reach 24 fps at 512x512 (StreamDiffusionV2, MLSys 2026 best paper). The best single-4090 prompt-conditioned stylizer peaks at 54.9 fps at 512x512 — with 0.5 to 1.0 SECONDS of end-to-end latency, because that throughput comes from batching 8 to 16 frames. For an overlay whose entire value is presenting fresh frames (the operator already chose --present-waitable for 99.9% freshness over 49.9%), a one-second pipeline delay is not a tuning problem, it is a category error. And a single distilled denoising step alone costs 10.65 ms at 512x512 on a 4090 with TensorRT — that is 2.5x the entire 4.16 ms budget of a 240 Hz frame, at a quarter of 1080p. Even NVIDIA's own tuned pixel-space diffuser on newer hardware takes a 5070 Ti from ~240 fps to 68.9 fps at 1440p, and it needs developer-authored engine masks PhyriadFG can never have.

WHAT IS ACTUALLY BUILDABLE, IN ASCENDING COST — three tiers, and the first two are real today:

TIER 1, PROMPT -> LUT/SHADER PARAMS (ships at 240 Hz, essentially free). An LLM turns the prompt into grading parameters or a 3D LUT ONCE, then a shader applies it per frame. Measured anchors: prompt-to-14-parameters in 1.38 s with a 250M FlanT5-base; a learned adaptive-LUT model under 600K params processing a 4K frame in under 2 ms on a Titan RTX, and trained at 480p it applies at 4K without loss; ShadAR already does prompt -> HLSL -> runtime-compiled -> live passthrough. Per-frame cost after the prompt is a trilinear texture fetch. Zero flicker by construction, because a LUT is a pure per-pixel function. This tier is fully compatible with PhyriadFG as it stands and needs no architectural change. It cannot add lighting or material detail — it changes colour, tone and contrast. That is a real limit, and it should be stated to the operator rather than sold around.

TIER 2, PROMPT -> FEED-FORWARD STYLE NET (plausibly 1080p at high refresh; needs measurement). The FastCLIPstyler architecture is exactly right for this constraint: a CLIP text embedding goes through a small MLP to a 100-d style vector ONCE per prompt change, and only a small conv net runs per frame. Measured 70.4 ms (24.9 ms for the Edge variant) per image on a 2070 SUPER — resolution unstated, which is the gap. The 1080p feasibility case rests on GameSR: 138K params, 26.56 ms per 1080p frame on a MOBILE Adreno 750. On a 4090 that class of network should be low-single-digit ms; that projection is MINE and unmeasured, and it is the single highest-value experiment the operator can run before committing to anything. Crucially, temporal stability here is bought at TRAINING time with a flow loss and costs nothing at runtime. This tier can change texture and look, not lighting.

TIER 3, DIFFUSION AT REDUCED RESOLUTION AND CADENCE (research, not shipping). Only viable at 512x512 with 0.5-1 s latency. If the operator wants to explore it, it should be a separate offline/screenshot mode, explicitly not the overlay path.

THE OPTICAL FLOW QUESTION — YES, GENUINELY REUSABLE, AND BETTER THAN THE LITERATURE'S. This is the strongest finding for PhyriadFG. The 2026 streaming stylization paper warps the previous DECODED frame with optical flow as its temporal conditioning signal, and its flow computation was 96% of an 882 ms latency spike (CPU Farnebäck), forcing 8 worker threads and async prefetch to get p95 from 1439 ms down to 756 ms. PhyriadFG already computes a dense GPU flow field per frame pair as part of its shipping R7(a) pure core — it would be handing this class of method its most expensive input for free. Three honest caveats: (1) SD latent space is 8x downsampled, so the flow must be downsampled and warping latents by RGB-space flow is an approximation; (2) occlusion handling needs a forward-backward consistency check, which PhyriadFG may not currently compute — worth checking against fg_core.comp before claiming it; (3) if the filter output is fed back into capture, the flow is being estimated on filtered rather than source frames, which is a feedback path that needs an explicit design decision.

TWO WARNINGS WORTH CARRYING INTO ANY GATE. First, scene cuts break every warp- and cache-based stabilizer (LPIPS-against-oracle jumps ~50% at hard cuts, with warping error staying flat and hiding it); PhyriadFG will hit menus, loading screens and alt-tab constantly, so cut detection is not optional. Second, and this fits the container's verify-before-claim discipline exactly: warping error as a flicker metric REWARDS SMEARING. The paper documents a configuration that improved εw from 18.34 to 12.96 while collapsing Sobel edge magnitude by 60% — a metric win that was a quality loss. Any filter gate must pair a temporal metric with a spatial-detail probe, the same way M4's oracle gate paired k with byte-exactness.

FINALLY, THE PLATFORM NOTE. VK_NV_cooperative_vector runs small MLPs inside Vulkan shaders on Ada, not just Blackwell. If Tier 2 is pursued, that is the right substrate for a Vulkan overlay — the per-frame net lives in the present shader rather than in a separate inference runtime, which keeps the no-injection constraint intact and avoids a PyTorch/TensorRT dependency in the hot path.
