## Dimension `identity`

### I-1 · The launcher fills --window with the window's FULL TITLE and the FG resolves it exactly once at startup

**CONFIRMED · severity medium**

**Why (verifier, verbatim):** Every link in the chain holds. ui/src/main.js:790 `opt.value = w.title;` stores the full title; the change handler at :723-726 copies `opt.value` into the --window text field; buildArgs `case "text"` pushes it verbatim (no re-validation at Start — I checked the whole Start path, nothing re-lists windows). ui/src-tauri/src/lib.rs:154-157 does document the field as "the substring the FG's `--window` flag matches against" while :622 pushes the untouched `title`. On the FG side cli.cpp:497 snprintf's the arg into `char window_substr[256]` (cli.hpp:95) and capture_init.cpp:413 is the only WGC resolution site; :414 emits WINDOW_NOT_FOUND and `return 1` on no match. `grep -rn find_window_by_substr src/ framework/` returns exactly the two call sites at capture_init.cpp:357 (DDA) and :413 (WGC), both inside init_capture_source before any thread starts; nothing re-matches later. I lowered high→medium only on consequence, not on mechanism: the failure is loud and non-destructive — a named reason code (compat_reason.hpp:32 WINDOW_NOT_FOUND), a printed line, exit 1 that the launcher surfaces, and a one-click retry. It costs the user a run, it does not corrupt one. Contrast finding 2, which fails SILENTLY on the same surface.

**Fix sketch (verbatim):** Stop keying on a mutable string: have list_windows return the pid (it already collects it, lib.rs:622) and add a `--window-pid` flag the FG resolves by GetWindowThreadProcessId, using --window only as a fallback. Minimal interim fix: in capture_init.cpp:413 retry find_window_by_substr for ~2 s before emitting WINDOW_NOT_FOUND, and have main.js re-invoke list_windows at Start to warn when the stored title no longer exists.

### I-2 · find_window_by_substr returns the FIRST EnumWindows match with no tie-break, no self-exclusion and no "N matched" warning

**CONFIRMED · severity high**

**Why (verifier, verbatim):** capture.cpp:90-98 is exactly as quoted: `struct WndFind { const char* substr; HWND found; }`, and the callback body is `if(IsWindowVisible(h)&&title[0]&&std::strstr(title,f->substr)){f->found=h;return FALSE;}` — substring semantics, first hit wins, `return FALSE` aborts the enumeration so later candidates are never even seen. `find_window_by_substr` at :97-98 returns `f.found` with no count, no score, no exactness preference, no class filter, and no owning-process check (GetCurrentProcessId appears nowhere in the file). EnumWindows walks top-level windows in Z-order, so "whichever superset title is nearer the front wins" is the actual selection rule. The contrast with the launcher is real: lib.rs:618 does filter by exe name (however brokenly — see finding 7), the C++ finder has no equivalent. lib.rs:638 `found.dedup_by(|a,b| a.title==b.title && a.exe==b.exe)` also holds — the vec is sorted by (exe,title) at :631-637 first, so the duplicates dedup_by removes are adjacent and really are collapsed. I keep high: unlike finding 1 this fails silently — the run proceeds, presents, and reports healthy stats while frame-genning the wrong window, and main.js:60's placeholder "e.g. Battlefield" actively invites the short substrings that make a collision likely.

**Fix sketch (verbatim):** Make enum_wnd_cb accumulate every match instead of `return FALSE` on the first, then choose: exact title equality first, else the largest client rect; skip windows whose GetWindowThreadProcessId equals GetCurrentProcessId. Print "N windows matched '<substr>' — using '<title>' (pid …)" whenever N>1 so the choice is auditable.

### I-3 · Captured window size read once, WGC frame pool never Recreate'd — mid-run resize/maximise/F11/DPI change crops or letterboxes for the rest of the run

**CONFIRMED · severity high**

**Why (verifier, verbatim):** capture_init.cpp:415-416 is the single size read: `RECT cr{}; GetClientRect(wgc_target_hwnd,&cr); if(cr.right>cr.left&&cr.bottom>cr.top){d.w=…;d.h=…;}`. NAT_W/NAT_H are then frozen as `const` at :424 and the pool is built from them at :193 + :199-200 (CreateFreeThreaded with `pool_sz{NAT_W,NAT_H}`). `grep -rn "Recreate" src/ framework/` returns ZERO hits — I ran it; the pool is never resized, and no WM_SIZE/WM_DPICHANGED handling exists on the capture side. The "truth fetched and discarded" claim also holds: `frame.ContentSize()` is read at :245 only inside `if(dp_on)` and `cap_item.Size()` at :166 only inside `if(cfg.dpi_probe)` — both default-off one-shot printfs. The readback is hard-wired to the startup dims (capture.cpp:508-512 and :543-547 memcpy `size_t(NAT_H)*nat_row`, `nat_row=NAT_W*nat_bpp`), so a grown window is cropped and a shrunk one leaves stale/undefined pixels — wrong content, no crash, no log line. One correction to the reporter's framing: the DPI sub-case is already KNOWN in-repo, not unnoticed — cli.hpp:97-99 names "the high-DPI capture-crop" as the very thing --dpi-probe exists to diagnose. The resize/maximise/F11 cases are unmitigated and undiagnosed. High stands: silent wrong output on the default path from a gesture (F11 / maximise) users make constantly.

**Fix sketch (verbatim):** The pipeline is init-sized (NAT_W/H thread into the staging ring, Vulkan images, flow/warp extents), so the honest small fix is detect-and-exit: compare `frame.ContentSize()` against pool_sz in the FrameArrived callback (it is already fetched there), and on a mismatch emit a new named reason (e.g. SOURCE_RESIZED) and set g_quit. The full fix is pool.Recreate + a staging-ring realloc, which needs a re-init path that does not exist yet.

### I-4 · On the default WGC window path the target window's monitor never selects the present monitor

**CONFIRMED · severity high**

**Why (verifier, verbatim):** The asymmetry is exactly as described. The DDA branch derives it — capture_init.cpp:359-360 `int _oi=d3d_output_index_for_monitor(MonitorFromWindow(wgc_target_hwnd,MONITOR_DEFAULTTONEAREST)); if(_oi>=0){ cfg.cap_mon=_oi; … }`. The WGC branch at :412-419 touches only d.w/d.h/d.fmt. My own `grep -rn "cap_mon *=" src/` (minus cap_mon_hz/cap_mon_src) returns exactly three lines: capture_init.cpp:360, cli.cpp:474 (--monitor), cli.hpp:16 (`int cap_mon=0`). I checked every `game_hwnd` use in PresentSurface.cpp (lines 223, 367-368, 580, 586, 588, 594, 598): it drives only the startup focus-restore and the foreground-yield test — never monitor selection. So PresentSurface.hpp:109-110's "Also picks our monitor via MonitorFromWindow(game_hwnd)" is documentation the implementation does not honour. The launcher makes this the default: main.js's --monitor control has default "0" and buildArgs' `case "number"` skips a value equal to the default, so --monitor is never even passed. **Fix sketch (verbatim):** Mirror the DDA derivation in the WGC branch right after :413 (`_oi=d3d_output_index_for_monitor(MonitorFromWindow(hwnd,…)); if(_oi>=0) cfg.cap_mon=_oi;`), placed before the :402-405 pres_mon default. Better: resolve pres_mon by HMONITOR against pres_outputs instead of copying an integer across index spaces, and either implement or delete the PresentSurface.hpp:109-110 contract.

### I-5 · DDA no-match fallback leaves game_hwnd null, making the default own-window presenter yield permanently

**CONFIRMED · severity medium**

**Why (verifier, verbatim):** Traced end to end. capture_init.cpp:357 resolves the handle; the else-branch at :362 prints "ninguna ventana visible coincide — usando --monitor %d (DDA)" and falls through with wgc_target_hwnd still nullptr. present_stage.cpp:40-45 then sets `psd.style=pp::Style::OwnWindow; psd.game_hwnd=(void*)wgc_target_hwnd;` → null. PresentSurface.cpp:598 `const bool want_yield = impl_->game_hwnd ? !(ours || game) : (fg != nullptr && fg != impl_->hwnd);` → with null game_hwnd, any other window holding focus yields; :601-602 sets yielded + yield_plane(); :607 `if (impl_->yielded.load()) return {};` presents nothing. **Fix sketch (verbatim):** In PresentSurface.cpp:598, when game_hwnd is null do not yield on a foreign foreground (the watchdog at :505+ and the dxgi_live exit already provide the no-lock-out floor); or bind a reference HWND for the monitor-capture case. Smallest local fix: at capture_init.cpp:362 either bail like the WGC path or set `wgc_target_hwnd=GetForegroundWindow()`, and correct the misleading present.cpp:1798 advice for the null-binding case.

### I-6 · A minimized window matches the substring, then the run produces nothing with no first-frame timeout

**CONFIRMED · severity medium**

**Why (verifier, verbatim):** Every code-side fact checks out. capture.cpp:94's only visibility filter is IsWindowVisible, which stays true for an iconic window, and my `grep -rn "IsIconic" src/ framework/ ui/` found hits ONLY inside prebuilt Rust/webview binaries — zero in any source file, so nothing anywhere rejects or notices an iconic target. capture_init.cpp:415-416's `if(cr.right>cr.left&&cr.bottom>cr.top)` guard means a minimized window's degenerate client rect falls through silently to the monitor-sized d.w/d.h set at capture.cpp:50-52. The C-thread spin is as quoted (capture.cpp:418-419 `for(int spin=0;…;++spin){ if(spin>=33) break; Sleep(1); }` then :423 `if(w==r) continue;`) — a bounded spin inside an unbounded loop, so it idles forever rather than hanging a thread. The death watchdog genuinely cannot fire: present.cpp:1953 requires `!IsWindow(wgc_target_hwnd)`, and :1947-1948's comment states the IsWindow gate exists precisely to distinguish death from minimized/occluded. compat_reason.hpp:27-39 lists all twelve codes and there is no NO_FRAMES; no first-frame timeout exists on the init or capture path. Two qualifications. (a) "No diagnostic" is overstated: present_stage.cpp:83 increments total_frames on every successful submit (including a yielded no-op), so the 1-per-90-presents stat line at present.cpp:2810/2951 does print with `cap 0/s`. What is missing is a NAMED reason and a bounded exit, not all output. (b) The "WGC delivers no frames for a minimized window" premise is OS behaviour I cannot verify by reading this repo — only the absence of any guard is code-verifiable. Worth adding: restoring the window does not cleanly recover either, because the pool is now monitor-sized against a smaller client rect, which is finding 3's crop.

**Fix sketch (verbatim):** At capture_init.cpp:413-416, after resolving the handle, add `if(IsIconic(wgc_target_hwnd))` → either wait for restore with a bounded timeout or bail with a named reason. Independently, add a first-frame timeout on the WGC path (no FrameArrived within N seconds → emit a new NO_FRAMES ReasonCode and quit) so every no-frames cause, not just the iconic one, terminates instead of idling.

**CONFIRMED · severity low**

**CONFIRMED · severity medium**

**Why (verifier, verbatim):** Every cited line is verbatim. ui/src/main.js:790 `opt.value = w.title;` with the exe only in `opt.dataset.exe`; the change handler at :720-728 does `const title = opt.value; ... wi.value = title;`. buildArgs' `text` case (:831-834) pushes `--window <that string>`. lib.rs:622 pushes `WindowInfo { title, exe, pid }` and `pid` appears in main.js exactly once, in a comment (`:694 // [{title, exe, pid}]`) — never read. So the whole contract really is one volatile string, and a title drift breaks it. Severity lowered from high: under the default WGC path the failure is a clean bail with a named reason (capture_init.cpp:414), the field is user-editable and takes a substring, and the product's primary target (a fullscreen game) has a stable caption. **Fix sketch (verbatim):** Carry the stable identity end to end: keep `pid` (and/or hwnd) on the option's dataset, add an FG flag `--window-pid <pid>` whose EnumWindows predicate compares GetWindowThreadProcessId instead of strstr, and have the dropdown emit that flag; keep `--window` as the manual-substring fallback when no pid is supplied.

### L-2 · Auto-restart's 600 ms `restarting` guard swallows the NEW child's fatal exit; launcher wedges at "running" with an inert Stop

**CONFIRMED · severity high**

**Why (verifier, verbatim):** Traced the whole loop. main.js:1035 sets `restarting = true` before `await invoke("restart")`; the 600 ms clear (:1046-1048) is scheduled only after that promise resolves, i.e. after spawn_fg has already returned — so the window covers the new child's entire early life. The new child's stdout reader has the CURRENT epoch (lib.rs:246-250), so on its EOF it takes the slot, waits, and emits `fg-exit` (lib.rs:326-345) — this is not an old-child event the guard was written for. main.js:1099 `if (restarting) return;` discards it before `setRunning(false)` at :1102, so `running` stays true, `btnStart.disabled = on` (:997) keeps Start dead, and Stop hits lib.rs:426 `guard.take()` → None → `Ok(())` with no event, while the click handler (:1082-1086) reacts only to a rejection. `is_running` is invoked exactly once, at DOMContentLoaded (:1119) — no other resync path exists (grep confirms 1119 is the only call site). The launcher is stuck until the window is reloaded. Timing: for the reporter's WINDOW_NOT_FOUND path the child must die inside ~600 ms (parse + layer parity + D3D11CreateDevice + DXGI enum at capture_init.cpp:368 — likely but not guaranteed); however finding 6(b) makes it certain — a bad raw-flags token exits at main.cpp:208 (`return cfg.parse_failed ? 2 : 0`) before any device work, in tens of milliseconds, always inside the guard.

**Fix sketch (verbatim):** Make the guard epoch-aware instead of time-based: include the child's epoch in the `fg-exit` payload and ignore only exits older than the epoch `restart` just created. Smallest stopgap: in the Stop handler, after `await invoke("stop")`, re-poll `is_running` and `setRunning(isUp)` so the UI can always resync.

### E-7 · Launcher's 600 ms restart guard swallows a fast child death

**CONFIRMED · severity medium**
